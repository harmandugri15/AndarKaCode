The core question

How the frontend and backend stay aligned

Six mechanisms stack on top of each other. Each one catches what the one before it might miss.

1 · One source of truth

A versioned Contract

A small JSON document lists the resource, fields, actions and rules. A Zod schema checks it. Every edit creates a new version with a SHA-256 hash.

2 · Told, not guessed

Instructions sent to Screenshot-to-Code

The Contract becomes text sent along with the screenshot: exact field names, data-field and data-action markers, and a SAMPLE_* constant.

3 · Both sides generated

Server and client from one Contract

The Express routes and the frontend's api.js client come from the same templates and the same Contract. The AI never writes the API calls.

4 · Checked by code

Conformance check + repair

We parse the generated JSX and confirm every marker exists. If any are missing, a narrow "update" job asks Screenshot-to-Code to add exactly those.

5 · Same version or stop

Sync Barrier

Integration starts only when the frontend hash, the backend hash and the current Contract hash are all equal. An out-of-date build is rejected and rebuilt.

6 · No URL mismatch

Same-origin app

The generated Express server also serves frontend/. The page calls /api/employees on the same origin, so there are no CORS or base-URL bugs.

Why parallel matters

Where the time goes

The total is about the slowest branch (the frontend on the GPU), not the sum of every step. The user's review happens during the wait, so that time isn't lost.

Measured: frontend about 5 min on the RTX 4060 (Step 2). Estimates until we measure them in Steps 4 and 12: Contract about 20–40 s, verification under 1 min. Backend generation is template-based, so it takes about a second.

Getting the most from free hardware

Seven efficiency rules this design follows

Keep AI output small

Generation time grows with output length. The Contract is about 300 tokens. Long code (the backend) comes from templates in about a second.

Use each machine for one job

The GPU laptop does the heaviest AI job (the HTML). The Mac does the short AI job and everything deterministic. No two models compete for one machine's memory.

Overlap human time with machine time

The user reviews the Contract while the GPU builds the page, so the wait does double duty.

Never compute the same thing twice

Screenshots, Contracts and jobs are keyed by hash (content-addressed). A repeat request returns instantly, which also makes retries safe (idempotent).

Use code where you can

Validation, routing, wiring and tests are all deterministic code. AI is used only where a picture has to be understood.

Constrain the model's output

Ollama's structured output takes the Contract's JSON Schema, so the model can only produce valid JSON. That means no parse errors and no retries.

Fail over, not fail

Local first; on error, timeout or invalid output, the same request goes to the backup key. Each result records which provider made it.

Two separate databases

builder_db on Laptop A stores our users, projects and jobs. The generated app gets its own employee_app database, set in its own .env.

GitHub permissions, asked only when needed

Login asks for read:user. The first Publish asks for public_repo + workflow (the second is needed to push the CI file). The token is encrypted with AES-256-GCM and never leaves Laptop A.

Safety

Only the Gateway is reachable on Laptop B, and it needs an API key. Previews run in containers with no secrets, on a different origin from our UI.

Practice

Viva questions

How do the two laptops stay in sync?

Laptop A owns all state and always starts the calls. Both sides build from one versioned Contract, every result is stamped with that Contract's hash, and the Sync Barrier only continues when the hashes match.

How do you know the frontend matches the backend?

The frontend is told the exact field names and markers. The API client and server are generated from the same Contract. Then we parse the JSX to confirm the markers exist, and run tests and a browser smoke test.

Where exactly is the AI, and why only there?

In two places: reading the screenshot into a Contract (our code) and generating the HTML (Screenshot-to-Code). Everything that must be exact, such as routes, validation, wiring and tests, is deterministic code, so it's reliable and explainable.

Why is a 5-minute generation acceptable?

It runs on a free local GPU, the user reviews the Contract during that time, repeated screenshots are cached, and the backup key can take over for the demo.

Why a Gateway instead of calling Screenshot-to-Code directly?

Screenshot-to-Code only has an internal WebSocket that may change. The Gateway gives a stable REST contract with an API key, a queue and a cache: the Adapter pattern.

How is the user's GitHub account kept safe?

We request minimal OAuth scopes only when needed, store the token encrypted, never send it to Laptop B or a container, and only create new repos, never overwriting existing ones.
